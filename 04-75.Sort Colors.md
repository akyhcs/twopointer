## Why?

Let's create a case where your code fails:

```text
[1, 2, 0, 1]
```

Initially:

```text

mid = 0
r = 3
```

```text
[1, 2, 0, 1]
 ↑
mid
```

### `nums[mid] == 1`

So:

```java

```

Now:

```text
[1, 2, 0, 1]
    ↑
   mid
```

### `nums[mid] == 2`

We want to move this `2` to the right.

Swap `mid` and `r`:

```text
[1, 1, 0, 2]
    ↑     ↑
   mid   r
```

Then:

```java
r--;
```

So:

```text
[1, 1, 0, 2]
    ↑   ↑
   mid  r
```

Now look carefully.

**What is sitting at `mid`?**

```text
[1, 1, 0, 2]
       ↑
      mid
```

It's a **0**.

We haven't processed that `0` yet!

But your code says:

```java
mid++;
```

So you skip over the `0`.

Now:

```text
[1, 1, 0, 2]
          ↑
         mid
```

Loop ends.

And the array is:

```text
[1, 1, 0, 2]
```

❌ Not sorted.

# Therefore

For:

```java
else { // nums[mid] == 2
    swap(nums, r, mid);
    r--;
}
```

**Do not move `mid`.**

Because after the swap:

```text
        mid
         ↓
[ 0s | 1s | ? | 2s ]
             ↑
          unknown
```

The element that came from the right side is **unknown**.

We need to inspect it again.

### Your three rules are therefore:

```java

    l++;
    mid++;
```

Because we know we've correctly handled the `0`.


Because `1` is already in the correct middle region.

Because the new `nums[mid]` is **not yet classified**.

That's why `mid` stays.

Your reasoning for `0` is correct about the **value at `low`**, but we also know something extra that makes it safe to increment `mid`.

Let's compare them.

### When `nums[mid] == 2`

Suppose:

```text
[0, 1, 2, 1, 0, 2]
       ↑        ↑
      mid      high
```

We swap `mid` and `high`:

```text
[0, 1, 2, 1, 0, 2]
       ↑        ↑
      mid      high
```

After the swap, the element that came from `high` could be:

```text
0
```

or

```text
1
```

or even `2`.

So we **don't know what `nums[mid]` is now**.

Therefore:

```java
high--;
```

but **not**:

```java
mid++;
```

We need to examine `mid` again.

---

## But what about `nums[mid] == 0`?

You're right:

> "We don't know what value `low` is holding. It could be `1` or `2`."

Exactly.

Suppose:

```text
[1, 0, ?, ?, 2]
    ↑
   mid
 ↑
low
```

We swap:

```text
nums[low] ↔ nums[mid]
```

giving:

```text
[0, 1, ?, ?, 2]
    ↑
   mid
 ↑
low
```

Now the important question:

**What value did we bring into `mid`?**

We brought whatever was at `low`.

Could it be `0`?

### No.

Why?

Because of our invariant:

```text
[ 0s | 1s | unknown | 2s ]
      ↑
     low
```

`low` is at the **boundary of the 0 region**.

If `nums[mid] == 0`, then `mid` is in the unknown region, while `low` is at the beginning of that unknown region / 1-region boundary.

The element at `low` cannot be an unprocessed `2` that needs to stay at `mid` in the same way as the `high` case.

More intuitively, after processing a `0`:

```text
[ 0s | 1s | unknown | 2s ]
       ↑
      low
```

The element swapped into `mid` is already from the region that has been classified as **not needing further inspection**.

That's why we can safely do:

```java
low++;
mid++;
```

---

### The easiest way to remember the difference

When we encounter `0`:

```text
mid → 0
low → already processed region
```

So after swapping, **both positions are handled**.

Therefore:

```java
low++;
mid++;
```

When we encounter `2`:

```text
mid → 2
high → unknown region
```

After swapping, the new `mid` came from the **unknown region**.

Therefore:

```java
high--;
```

but:

```java
// mid stays
```

So your observation is excellent:

> **Both swaps bring another value into `mid`. The difference is where that value comes from.**

* `0` comes from the **left boundary**, whose region is already processed.
* `2` comes from the **right boundary**, whose region is still unknown.

That's the real reason behind the seemingly strange rule:

```text
0 → move mid
2 → don't move mid
```
